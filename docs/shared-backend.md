# Connecting real shared accounts, reports and photos

The project is still in demo mode until a real Supabase project is configured. No project URL or public app key was present during this delivery. Nothing was deployed to a hosted project. Local SQL role tests and a Deno type check are not a hosted integration test.

1. Create/select a Supabase project. Copy .env.example to the ignored .env.local and set EXPO_PUBLIC_SUPABASE_URL plus EXPO_PUBLIC_SUPABASE_ANON_KEY to its public publishable/anon key. These are mobile public configuration, protected by RLS. Never put a service-role/secret key in any EXPO_PUBLIC variable, chat, Git commit or mobile bundle.
2. For a populated database with only the initial v1 migration applied, first run supabase/upgrade-from-v1.sql as the database owner. This narrow preflight preserves hidden rows and timestamps during the older details backfill. A database already on v2 needs only the new third migration. Never rerun an applied migration. Use the Supabase SQL editor to apply all three versioned migrations, in filename order, once each. Alternatively, authenticate the Supabase CLI on your own machine, `npx supabase link --project-ref YOUR_PROJECT_REF`, then `npx supabase db push`. Enter database passwords only in the CLI's secure prompt. Do not rerun a migration already applied.
3. Deploy the private photo handler with `npx supabase functions deploy observation-photo --project-ref YOUR_PROJECT_REF`. The hosted Edge runtime supplies SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY on the server; they never belong in the mobile configuration. supabase/config.toml deliberately disables gateway-only JWT verification because the handler must allow anonymous reads of *approved* media. The handler verifies actual users through Auth before every upload, removal or private read. Do not replace that check with unverified JWT decoding.
4. Enable email/password Auth and email confirmation; configure mail delivery, redirect URLs, CAPTCHA and Auth rate limits before public launch. Restart Metro after .env.local changes. Add the specific project hostname to the cloud network policy if testing from this managed environment; the public project URL is sufficient to identify that hostname, not a secret key.
5. Run `npm run backend:check` from the project directory (Node 24+). It reads .env.local, prints no key values, and checks the public schema, bounded spatial RPC and deployed photo endpoint. The check refuses a secret/service-role key. A successful run still does not verify email delivery or authenticated flows.
6. Create two test users through the app and confirm their email addresses. On separate sessions/devices, submit a report with species/count or road conditions, a selected event time, selected place and optional photo. Verify the second user sees the report and typed details but cannot see the pending photo, private profile or reporter ID, edit the report, or call moderation RPCs.
7. Provision one trusted moderator through server SQL (`insert into public.moderators(user_id) values ('TRUSTED_AUTH_USER_UUID');`). Sign in as that account and use Account → Moderator review → Review attached photo. Inspect the actual image and enter a reason before approval. Photo approval is a separate decision from report review. Check it becomes visible to the other user, and that hiding the report hides its approved media. Existing signed URLs expire within 60 seconds; content already viewed cannot be recalled.
8. Simulate upload failure. The report remains saved, and Retry photo attachment uses that same report ID; it never creates a second observation. Remove my photo deletes the private object and metadata through the owner-checked function. Replacing a deleted photo begins moderation again.

## Security and operating limits

Public report reads return rounded locations, a chosen place label, report kind, details and observed/submitted times; never author_id. Reports are limited to five per user/hour, flags to twenty/hour, and photos to one per report. Storage is private; a restrictive policy prevents broad existing policies from granting direct access to the photo bucket. Clients cannot insert media rows, directly upload originals, or self-approve. The Edge handler generates paths and repeats metadata stripping on the server. Only sanitizing code imports are shared with the app; service-role handling is in the excluded server entry point.

Images are resized to at most 1280 pixels along the longer edge and re-encoded as JPEG, then EXIF/XMP/IPTC/comments and trailing payload are removed. The server also limits JPEG dimensions (2048 max), structure and size (2 MB). The app requires a privacy check before submission. This does not detect faces or unsafe scenes automatically; images stay private until reviewed. Demo mode stores sanitized photos only on the device with a 4 MB photo budget and an explicit removal control.

Before a public launch, add gateway-level per-user/IP upload and signed-URL throttling, resource monitoring, mail abuse protection, production geocoding/tiles, a retention/deletion policy and real hosted cross-user integration tests. The app does not claim these operational tasks are complete.
